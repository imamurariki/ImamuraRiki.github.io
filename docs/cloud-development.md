# iPhone中心の開発・レビュー運用

開発依頼 → Codexが最新mainから専用ブランチ作成 → 修正・検証 → コミット・push → main向けPR → ユーザーがGitHubでレビュー・マージ、を標準とします。詳細はルートのAGENTS.mdに従います。公開は既存のGitHub Pages設定に従い、mainにマージするまで行いません。

## 設定の役割

- AGENTS.md：リポジトリを読むエージェントへの作業ルール。権限を付与するものではありません。mainへマージした後、新しいタスクでも取得できるようになります。
- CLAUDE.md：サイト固有の注意事項。Git操作はAGENTS.mdに統一しています。
- Codex環境のstart_skill：起動・検証・開発手順。設定下書きの保存と、実行中環境への適用・Publishは別です。
- Codex環境のネットワーク設定：api.github.comへのHTTPSアクセス。許可してもGitHub APIの認証や書込権限は付与されません。
- GitHub連携：対象リポジトリへのアクセスとPR作成権限。プラットフォームのGit HTTPS認証とgh/API認証は別経路です。

## 今回確認した障害（2026-11-06 JST）

Git fetch/pushはHTTPSのorigin経由で成功しました。一方、api.github.comへのcurlはCONNECTトンネル確立時にプロキシ（envoy）から403を受け、ghのREST APIもForbiddenになりました。稼働中環境はrestricted、カスタム許可先は空です。api.github.comの追加は設定下書きにのみ存在していました。

ghは導入済みでGH_TOKENの存在を確認しましたが、値は確認・出力していません。GitHubへ到達する前に拒否されるため、APIトークンの有効性、対象リポジトリへのPR書込権限、GitHub連携アプリの権限は未検証です。この403だけで認証失敗とは判定できません。このセッションには標準PR作成ツールも公開されていませんでした。

## 設定反映後の再検証（2026-11-06 JST）

ユーザーによる環境のPublish後、稼働環境でapi.github.comの許可がenforcedになったことを確認しました。既存の認証を使った `gh api user` はHTTP 200で成功し、対象リポジトリの権限取得、GraphQL経由のPR一覧取得も成功しました。追加トークンの登録は行っていません。前回の通信拒否は、下書きの許可設定が稼働環境に未反映だった問題として解消しました。新規タスクでの復元・認証の再注入は引き続き未検証です。

## 再発時の設定確認手順

この作業環境から設定下書きは保存できますが、Publishの操作は提供されていません。iPhoneの実画面は検証できていないため、以下は設定項目を基準にした手順です。アプリ内に項目がなければSafariでCodexを開いてください。画面名・配置は製品バージョンにより異なります。

1. 対象リポジトリに紐づくCodexの環境設定を開く。
2. インターネットアクセスの制限付き許可先に `api.github.com` が含まれる下書きを確認する。既存のパッケージ管理用プリセットは維持し、全インターネット許可にはしない。
3. start_skillの新しい開発手順も確認し、設定を保存して環境をPublishする。
4. このタスクで再検証を依頼する。稼働中環境への反映が確認できなければ、公開した環境を選んで新しいタスクを開始する。変更の自動伝播や復元成功は仮定しない。
5. API到達後に401や権限エラーが発生した場合のみ、CodexのGitHub接続と対象リポジトリのアクセス許可を確認する。連携が提供するPR作成機能を優先する。別のAPI資格情報が必要と確認された場合は、環境の安全な資格情報設定を使う。チャットやリポジトリにトークンを貼らない。

許可反映後、エージェントはruntime status、`gh api user`、対象リポジトリのPR一覧取得を確認し、既存の同じhead/baseのPRがないことを確認して実際の変更からPRを作成します。認証済みでも書込権限は作成成功まで未確認です。成功時はPR URLを報告し、ユーザーがGitHubアプリで差分・チェックを確認してマージします。MacBookの起動はこの流れには不要です。

新しいタスクでの復元、通信・認証・PR作成までの成功は、新しいタスクで実証する必要があります。今回の設定保存だけで完全自動化が検証済みになったとは扱いません。
